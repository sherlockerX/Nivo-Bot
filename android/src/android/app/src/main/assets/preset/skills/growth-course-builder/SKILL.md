# 建课框架

课程服务规定课程与进度的状态，模型负责探索需求、设计练习和解释依据。能力尚不清楚时不要求先起名称，不根据一次回答给人格结论。每次只问一个影响课程方向的问题，允许用户跳过或提出不同理解。

## Coach原生协议

本协议适用于Android主聊天和教练页发起的建课、改课，以及从旧能力列表跳转的建课。唯一权威写入口是`coach_command`，读取用`coach_query`。

1. 先用`coach_query`读取当前草案、课程与版本。使用精确对象ID，不从旧聊天猜测当前状态。
2. 用户提出培养目标或真实困扰后，用`new_draft`保存当前用户的原话；已有草案用`revise_draft`调整。探索时不创建正式课程、不切换旧能力绑定。
3. 先明确希望改变的具体表现、合适的练法和可行的实践机会。课程有顺序，但不同能力的证据标准不同，不统一套用角色对话或0到4分。
4. 用`propose`提交结构化课程，展示课程目标、顺序、每个单元的焦点、方法、证据条件与来源限制。先提出可审阅版本，不把提交提案说成已创建课程。
5. 等用户在后续消息明确确认所审阅的具体版本，再用`activate`提交`draftRevision`。不能用提出提案的同一条消息代替确认；有多个待确认提案时先明确用户指向哪一份。修改目标后旧提案失效。
6. 只在工具返回成功后说明实际保存或激活结果；失败保留草案，重新读取状态后处理，不宣称已经建好。用户无需为了确认再跳页面。

禁止直接写入`SKILL.md`、`books/`、`FRAMEWORK.md`、`ADJUSTMENTS.md`或Coach快照来创建、激活、重建、推进课程。禁止使用文件工具、shell、普通Markdown块或旧评分块代替原生命令。已有课程文件只读作为历史来源，`FRAMEWORK.md`和`ADJUSTMENTS.md`保留原文。

如果当前对话没有`coach_query`或`coach_command`，说明需要回到可用的主聊天继续；不要绕过工具改文件，也不要自动创建另一门课程。用户明确要求导出资料时可另做文件导出，但导出不代表课程激活或进度更新。

## 课程提案

`propose`的`payload`是JSON对象序列化的字符串，包含`course`和`sourceStatus`。`course`至少包含：

- `id`、`title`、`place`、`kind`、`version`、`source`；`kind`使用工具允许的能力类型，场所贴近真实生活。
- 有顺序的`units`，每个有`id`、`title`、`focus`、`method`、`criteria`、`source`。
- 每条`criteria`有稳定`id`、可观察的`description`与`requiresRealAction`。单元要求发出邮件、真实交流、参加会议、请他人反馈、持续执行或回访时，相应标准设为`true`。模拟讨论、草稿和计划不能替代已经发生的行动。

保留已有课程时先查询课程详情，使用真实课程ID提出修订。历史会话与原始回答不改写；新版标准不能自动继承旧评分为掌握。

## 教学与来源

从用户希望改变的表现倒推单元顺序，一次只训练一个焦点；可以解释必要理论，但不为凑书单固定要求10本书或L1到L5。对表达、判断、多视角、领导、执行等能力选适合的方法，单元完成标准要能以用户独立表现或现实报告核对。

参考书籍和方法时优先核对用户提供材料、出版社目录与试读、作者文章以及可靠综述。不要编造书名、引文、研究结论或作者经历。自拟练习用`sourceStatus:self_authored`并说明范围；只有实际核查过的来源才用`verified`。来源无法核实时标`unverified`，不得把未核实提案直接激活。来源限制同时保留在课程和对应单元的`source`中。

## 激活前自检

- 目标来自用户的实际困扰或明确认可，而非模型推断。
- 课程顺序、焦点、方法、标准和来源可审阅；单元ID唯一且稳定。
- 理论说明、模拟情景与现实行动各有明确用途，没有用标点位置推断语义。
- 每一项现实行动都需要用户报告，写好了不等于发出去了，模拟做到不等于现实做过。
- 用户确认的是当前`draftRevision`，确认发生在提案之后。
- 已执行结果来自工具成功返回，失败和证据不足如实说明。
