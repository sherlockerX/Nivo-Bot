# Nivo iOS local port

This page describes the local port of Android additions to the native iOS app. Source lives under `android/src/ios/NanoMuse/`. This work is in development and has not been published. It does not establish that the full iOS application builds or that phone interactions work.

## Navigation and daily work

Finished focus sessions now offer **Record reflection** from the immersive completion screen and the record list. The immersive screen closes before opening the fragment editor, where the completed session and its valid linked task are preselected. The initial date is the session's local completion day. Each session has its own draft; reopening preserves edits and removed links, or opens the already saved entry. This route never changes a task's status. Conflicting restored drafts or separately published entries are preserved and reported as conflicts instead of silently dropping text. The text field is labelled **Reflection** in all nine locales. The focus home page shows the latest three completed sessions, with their full start and end dates. Published reflections retain the task status and focus interval captured when saved, including after a source is deleted. Missing historical timestamps remain unknown. Both JSON and Markdown query results keep each reflection with its own saved links.

The Nivo shell includes main chat, daily fragments, Coach, goals and the library. Tasks and Focus are accessible below Ideas in the drawer. Secondary task views and Coach archives open from header actions. The classic chat layout has a toolbar menu for fragments, Coach, Ideas, Tasks, Focus and scheduled tasks, using the same navigation routes as links.

Course and idea details close before opening another conversation or editor. Classic-layout course requests fill a main-chat draft, and ordinary ideas prepare a separate conversation. Existing draft text and attachments are preserved, and preparation shows a loading state. Pending actions retain their source account generation. Main-chat restoration excludes practice conversations, dedicated routine conversations and remote read-only sessions; a newer navigation choice or account change invalidates an older asynchronous lookup. These presentation and host-integration paths still require Apple-platform validation.

- Tasks include editing, status changes, reusable groups and tags, search, a calendar, a priority matrix, group/status views, completion-tag statistics and local JSON import/export.
- Focus includes a countdown, stopwatch and break timer, task snapshots, pause/resume/finish, records and time statistics. Starting focus does not complete its linked task. Breaks and deleted records are excluded from focus statistics.
- Immersive focus uses a vector background or a picture selected from the phone. Imported backgrounds are saved per account, can be selected again and can be removed. The app restores active focus when brought to the foreground. Its full-screen view cannot appear above the iOS lock screen.
- Daily fragments include day/week/month/quarter/year views, text, mood, habits, photo selection and crop metadata, drafts, a recycle bin, task status selections and links to measured focus periods. Publishing a fragment and changing linked task statuses use the same transaction.

Selecting a task now opens a detail page with notes, dates, status, completed focus time and the three most recent completed focus sessions. Completion can use a past date and rejects future dates. The detail page can preselect that task for focus, including an already completed task, and open a linked fragment at its saved date. Editing keeps its own draft. Linked-fragment previews use text only. These routes check the source account generation before opening another page.

Editing an older fragment preserves the task title and status saved with that fragment. Keeping an existing link does not require a task that may since have changed or been deleted; requesting a new task-status change still checks its current revision. A task's completion date can differ from the fragment date. Habit-only check-ins save the day's habit status and mood without creating an empty diary entry. Changing a fragment's date or removing its habit mark preserves other records for the old day, and older drafts without a check-in instruction keep the existing mark. Discarding a draft first stops and drains autosave, so a late save cannot recreate it. Twenty-one real repository tests cover fragment transactions and these history rules; editor and photo interactions remain untested on iPhone.

Focus notifications select their exact saved record even after the timer has ended. A missing, deleted or foreign-account target does not fall back to an unrelated running timer. Returning after a countdown ends can show its completion screen. A task with another active timer shows the existing-session conflict instead of starting a second timer. Fragment loading failures remain visible with a retry action; opening a saved draft waits for the draft list to close.

The ordinary Focus page and immersive view share remaining-time rules for countdowns and elapsed-time rules for stopwatches and completed sessions. Both visible pages check expiry in the foreground; seconds update locally, and the repository is queried only when a running session needs settlement. An unchanged store revision no longer republishes all task, fragment and focus lists. The group distribution includes a ring, percentages and text rows, calculated together from completed intervals and the task-group snapshot saved at focus start. Intervals crossing a date boundary contribute only their overlap with the selected period.

Starting focus from the page binds the chosen background to that session. Choosing a different photo for the next session does not change the current one, and an AI-started session uses the vector background. Deleting a background clears its local selection and session reference. Full-screen restoration and keep-awake choices belong to each account; a late close cannot dismiss a newer session. The classic layout now restores immersive focus as well. Legacy global restoration settings are migrated only when the archive confirms ownership. Eleven portable preference/display tests and a real-store expiry/reload case cover these rules; image decoding, view lifecycle and system idle behavior still require Apple-platform execution.

The repository uses revision checks, exact operation receipts and account-generation checks. Each candidate snapshot is validated before its atomic write, including its account ownership, so a successful operation cannot leave an archive that fails validation on reopening. A failed disk write must not publish a successful result. A task's modification timestamp cannot move backwards when the device clock is corrected; completion and deletion retain the actual recorded time.

Native task editing, category management, row actions and focus controls now pass the account scope captured when their page or row was displayed. The model requires this scope instead of borrowing whichever account is current when an asynchronous button task starts. Changing account or restoring a backup invalidates open editors and queued controls; reloading an edit also checks its scope after the read. This host/UI wiring has been reviewed and syntax-checked, but has not run on an Apple platform. The task calendar now shows per-day task markers, a separate undated-task section and a horizontal date strip on narrow layouts or large text sizes. ## Coach and Daily practice

Coach is the course and progress archive. Selecting a topic opens its conversation in the Daily practice group. Lessons record source messages, training points, explanations, attempts, hints, assessments and summaries. A case can continue over several lessons.

Main chat can create and revise a course draft, propose a curriculum and activate it after a subsequent explicit user confirmation bound to that proposal revision. A topic conversation only accesses its own lesson context. The course list exposes pending drafts and a route back to main chat. The training calendar uses saved lessons and turn times.

Courses that require criteria review now have a review action on the map and course detail. It fills a main-chat draft asking to retain the course ID, source and order, compare simulation and real-action requirements, and show a proposal before activation. It does not send or activate automatically. Initial loading failures have a persistent retry state; a failed refresh keeps the last loaded archive with an error. A late retry or mutation completion cannot reopen another account or replace its page state. These UI and repository-host paths still need Apple-platform execution.

The topic-v3 rules separate understanding, application and delayed review. A hidden tool response does not count as visible teaching. A prompted attempt is not independent performance. A simulated answer does not satisfy a real-action criterion. The old training-card archive remains available for review and does not manufacture progress in new courses.

Starting a new lesson first recovers pending chat-to-archive writes and then reloads the archive revision. The store also rejects a new lesson while that conversation has unprocessed or damaged archive entries. This prevents a completed lesson's delayed final reply from being rejected against a newer lesson. Reopening the current lesson remains possible. The real archive store, outbox and bundled curriculum now run in the portable package, including loading retries and three regression cases for this ordering failure; the SQLite reconciliation and UI still need an Apple host.

Coach controls and course, draft, lesson and calendar sheets now retain the account generation that displayed them. Account changes and backup freezes invalidate these selections and delayed navigation, including a restore back into the same account. The conversation coordinator requires that captured scope throughout opening, resuming and restoring model bindings. Read-only chats expose the archive without pause or end controls. These host and sheet changes have source review and syntax coverage; their asynchronous presentation still requires Apple-platform validation.

Lesson archives now use the current saved state rather than a snapshot captured when the sheet opened. They separate understanding, application and delayed-review evidence, show the original criteria and quotations, and retain summary sources, corrections and unresolved hypotheses. Changed or deleted sources are marked, and earlier course versions remain historical records rather than current achievements. Real-world reports are labelled as the person's own reports. A read failure offers retry instead of presenting the record as deleted. The course map shows demonstrated units, with an explicit next-unit action that checks sources again and includes the unit the person actually saw; a stale page cannot skip a newly advanced unit. Paused courses and courses or units awaiting criteria review also reject advancement at the command boundary. Four progression regressions cover these rules. Native archive rendering still requires Apple-platform validation.

Opening an archive quotation targets its actual saved message ID. A merged assistant reply retains all of its source IDs; a missing or ambiguous source offers an unavailable notice instead of guessing by text. The request waits for the intended conversation, its loaded list and visible unlocked page, and is consumed once. Account changes and same-account restores revoke it. Reply persistence fixes the lesson and display-message identity before awaiting storage, so an older reply cannot borrow a later turn's identity. Portable tests cover navigation decisions; sheet dismissal, list layout, highlighting and interruption during persistence still need Apple-platform execution.

The bundled curriculum is generated from Android sources by `scripts/ios-coach-curriculum.py`. Explicit fields preserve theory, scenario and real-action requirements. `scripts/ios-preset.py` owns the other preset resources.

## Routines

The current port supports multiple daily times, custom weekdays, date bounds, minute intervals, dedicated or existing conversations, rerunning from a user message, model/model-group selection, failure counts, automatic pause and run history. User tasks in dedicated-conversation mode reuse one conversation in the Scheduled tasks group. Deleting it causes the next run to reserve a new conversation. The reservation is persisted before creation; the conversation and its group are created in one SQLite transaction. Clearing a task's explicit model uses the current default again. `minis-scheduled` exposes implemented operations through the existing permission manager; unsupported options are rejected explicitly. Saving an enabled task checks that its conversation, rerun message and model are available. Cancelling the editor cancels a save that has not yet committed.

Accepted requests are stored with their run IDs. Starting a run moves the request into history in the same write. After a restart, requests that have not started remain queued; interrupted runs are not automatically replayed. A completion receipt preserves the result if updating the main archive fails. Replaying that receipt does not execute the model again or increment failure counts twice. History keeps up to 50 runs per task, with a bounded result preview and a link to the conversation.

Notification options include `always`, `on_change`, `on_failure` and `never`, an optional title, silent notifications and account-specific quiet hours. Quiet hours default to `01:00-08:00` and can cross midnight or be disabled. Deduplication uses successful notification submissions, not just an intention to notify. `--dry-notify` records the run without submitting a result notification.

Script routines now have a source implementation for persistent home storage, interpreter/time-zone preflight, bounded file reads, literal arguments, version-specific approval, separate execution contexts, bounded standard output/error and cancellation that waits for native completion. Legacy rootfs home files are archived before migration; conflicts keep the current file and the original archive. Execution uses the exact script body and arguments that the person reviewed. `report` is accepted only from a live host-issued execution context; supplying task IDs or environment variables cannot grant that authority. Native exit codes and transport failures take precedence over an earlier success report. Debug, session-output, stdout logging and required-output options are parsed and connected to the runtime.

These script paths still need an Apple-platform build and runtime tests for native process cleanup, approval presentation, safe file descriptors and kernel integration. iOS does not guarantee arbitrary background model or script execution. Due routines run while the app is active. Local notifications invite the person to reopen it. A queued request is not reported as a completed run. The existing offload permission manager and the additional fixed-version script approval are the iOS enforcement boundaries; they are not a claim that Android's entire ShellGuard/RiskGate implementation has been ported.

Chat, Coach and routine model selection share a text-input/text-output capability check, provider availability and credential requirements. Dedicated image/video, embedding, ranking and moderation models are excluded from conversation choices. Explicit choices and automatic fallback use the same eligibility rules. Provider integration tests still require the application target and actual service access.

## Accounts and backups

Tasks, focus and fragments share an account-scoped store. Coach has an account-scoped archive and a journal for chat/archive reconciliation. Current user evidence is loaded from saved chat messages, not AI-supplied identity fields.

Concurrent sign-in and sign-out operations wait for an exclusive transition. Backup cannot start while a transition is active or queued. Account-file switching now copies both sides before replacing active files and keeps a recovery journal. Credentials change after the target files are installed; startup uses the recorded credential digest to finish a committed switch or restore the original files. Copy failures preserve the originals. API keys are kept in the device Keychain, not the journal. Errors remain visible with a retry action. Chat and sync work must finish before switching, and cached chat or voice objects check their account ownership before sending. Shortcuts also perform account recovery on cold launch. File-transaction tests cover these storage rules; Keychain, provider-mirror, startup and SQLite integration still require Apple-platform tests.

The personal-data category in `.minisbak` includes life data, Coach data, associated local media, routine settings/history and persistent script home files. Imported new routines start disabled; remembered execution approvals are not imported. Restore checks file manifests, path boundaries, sizes and SHA-256 digests, preserves conflicting local files, and verifies a staged copy before installing it. A missing recovery journal is distinct from a damaged or unreadable journal: the latter keeps personal-data access blocked and preserves recovery snapshots. Startup and shortcuts reconcile backup recovery before opening account repositories.

Restore now prepares all rollback snapshots before writing its journal or modifying live files. The journal identifies the run and its complete snapshot list. Recovery validates the whole list before replacing any directory; missing path markers, mismatched runs and ambiguous legacy snapshots keep the recovery barrier in place. Restoring copies the saved original, and snapshot cleanup follows successful journal removal. These file rules have portable tests; an interrupted import through the application remains an Apple-platform acceptance item.

Provider restoration now snapshots both the JSON mirror and the authoritative SQLite database using SQLite's online backup API, including committed WAL data and local selections. Empty or damaged database snapshots are rejected before replacement. Full-configuration writes are serialized, check every database step and propagate errors to restore and account-transition callers. Restore waits for initialization and queued writes, drains older deferred publications and invalidates older model-list requests. Database, JSON and caches are restored before the recovery barrier is released. Portable tests exercise the SQLite primitives and write queue; application-level provider integration tests have been added but have not run.

Credential restoration prepares a journal receipt containing target identifiers and a unique insertion marker, without secret values. It inserts only missing credentials, reads each insertion back before counting it, and preserves credentials that already exist or arrive concurrently. Rollback removes only entries still carrying that restore's marker; later environment-variable or MCP updates revoke the marker. Environment metadata has a file rollback snapshot and does not rewrite the imported Keychain values. Restore reporting counts verified provider, environment-variable and MCP credential insertions. The receipt rules have portable coverage; the Security framework implementation and its three Keychain tests still require an Apple host.

Provider-only restoration also holds an account and synchronization reservation. Thinking-rule edits reserve their direct database writes and are refused during restoration. Explicit cloud sends reserve access from snapshot construction through acknowledgement; new inbound changes wait for restoration. Whole-configuration provider merges now await persistence before confirming reception, retain the quiet-window rule for UI publication, and reject a merge if local configuration changed while waiting. Their application tests have not run. CloudKit automatic-send timing and the ordinary row-merge paths still need separate verification, so these changes do not establish atomicity for all cloud synchronization.

V3 provider, model, group and thinking-rule row merges now throw database failures through the receive checkpoint instead of treating them as version skips. Model deletions remove legacy and canonical IDs in one checked transaction. Incoming thinking rules check the persisted provider, so UI publication delays do not discard rules; missing parent records keep the batch eligible for replay. Updating a provider uses SQL UPSERT instead of REPLACE, preserving its existing models. The cascade deletion was reproduced and fixed by executing the production schema and SQL with real SQLite.

V3 cache refresh now reads a complete checked database snapshot and writes only the JSON mirror. Failed or partial reads preserve the previous cache. Legacy model IDs are persisted independently, including across full configuration saves. Repeated incoming records also schedule refresh, so an earlier cancelled or failed publication can recover. The write queue distinguishes mirror failures from full-configuration failures: refreshing a mirror cannot clear an unsaved local edit. Empty model lists retain automatic discovery, and duplicate display folding keeps a stable order without sending model-deletion records. Thinking rules are read in one database query with their persisted parents; restore propagates cache-read errors. The 31 provider application tests are written but unrun. Ordinary configuration saves now apply the actual field changes inside a database transaction instead of replacing the whole database. Unseen remote rows, unchanged fields and extension metadata remain in place. Model overrides merge changed keys, group membership keeps add/remove timestamps, and a remotely deleted row is not silently recreated by an old page. Database-write retries retain the earliest uncommitted baseline; explicit backup restoration still replaces the full configuration. The delta-writing core has real SQLite tests, while application queue integration and other ordinary merge handlers still require review and Apple-platform validation.

Incoming model payloads and group member histories are validated before a write can be acknowledged. Legacy flat deletion maps and current added/removed envelopes are both supported. Malformed values and unsupported routing strategies leave the batch eligible for replay instead of poisoning the cache. Initial database creation now includes both group-history columns and uses the same checked transaction as historical column repairs; a failure cannot stamp a completed migration version. The missing-column failure was reproduced with production SQL before the schema change.

Local field edits advance their stored update timestamp even if the device clock moves backwards. Model override edits also advance their separate user-intent timestamp, while a metadata-only refresh preserves that timestamp. Group removals and re-additions advance only past history the page has already observed, so newer unseen remote events retain their merge priority. The page records those event times before persistence to support rapid successive edits. Real SQLite regression tests first reproduced clock-related failures and then passed with the fix. The rapid-edit application test and full multi-device synchronization still require an Apple host.

Configuration retries also persist an unchanged in-memory snapshot after an earlier disk failure, and retrying a local full snapshot registers its complete current contents for synchronization. Branch configuration writes are reserved until publication and reject intervening changes. Restored API keys use their marked Keychain entry creation date for conflict comparison; this Security-framework path has not run here.

Task JSON supports Android v1/v2 documents and keeps foreign receipts as archival history rather than executable authorization. New iOS task events retain original snapshots for export. Older events without snapshots are not reconstructed from current fields. Real Android/iOS round trips and interrupted whole-backup recovery remain to be tested.

Nine task/focus transfer tests and five personal-data merge tests now execute the production codecs and repositories in the portable package. They cover repeat import, retained local edits, missing fragment links, invalid completion dates, failed writes, archival event receipts, account rebinding and measured focus export. Thirteen AI command/parser tests also run directly, including stale revisions, retry snapshots, category recreation, paused-time preservation and strict JSON types. This does not validate the application's foreground gate, current-user evidence lookup or a live model exchange.

Incoming cloud chat changes share conversation reservations with local edits and scheduled runs. Failed or cancelled deletion preserves the previous checkpoint for replay after restart. Backup and account transitions also check incoming work. Stopping or resetting sync cancels pending checkpoint writes, and callbacks from a replaced engine cannot rewrite its old state. CloudKit event delegates await their local handoff to preserve the API's event order; signing in does not recreate the engine in a loop. Ordinary message and summary merges now verify their conversation ownership and propagate SQL failures. A missing parent keeps the batch available for replay. Inserting a message and moving later sort positions commit together; updating a summary retains its old context until the replacement succeeds and does not queue the incoming summary for upload again. Dissolving a conversation folder clears membership, removes the folder and writes its deletion marker in one transaction. Explicit backup restoration can recover a previously deleted folder. Missing, oversized or unreadable message assets fail instead of becoming an empty reply, and the relay marks a received message as known only after its database merge succeeds. Real SQLite and file tests cover these rules. Five additional ChatStore application tests cover ownership, malformed payloads, ordering, folder rollback and summary preservation, but have not run on an Apple host.

Session metadata and the import of older reference messages now share one checked transaction. A failed message import preserves the previous title, group and pin state instead of leaving a partially updated conversation. Reference payloads use the application's real content and usage decoders before writing, and duplicate message IDs cannot overwrite another conversation. V1 and V2 reception propagate failures; V1 reference-session writes also preserve newer versions. Nine production SQL tests passed, and two additional ChatStore integration tests are awaiting an Apple host. Existing pin conflict behavior is unchanged: without a separate pin-action timestamp, a remote unpin cannot reliably override a local pin. Credentials and other ordinary mergers still need review; these changes do not establish lossless synchronization for the whole application.

Startup reference backfill now commits all imported rows and its completion marker in one database transaction. Failure preserves the reference rows and permits retry during foreground synchronization. Existing local messages and session metadata remain in place. Multiple reference devices are ordered by their known modification version; legacy rows without a version use their creation time. Deletion markers are checked before decoding removed message bodies, so a malformed deleted copy does not block valid content. Account, restoration and conversation-edit reservations cover the migration.

Legacy reference messages commit their placeholder session and body together, and older replays cannot overwrite a newer copy. Individual message deletion accepts current message IDs and historical composite names, then commits reference cleanup, local deletion and deletion markers together. V2 session deletion also clears legacy references. V1 whole-session deletion keeps the local conversation and clears only the source device's reference copies. Failures remain eligible for replay. CloudKit reception, foreground retry and concurrent restoration still need Apple-host validation; local clear-chat, retry truncation and relay deletion use the transactions described below. Relay checkpoint persistence and obsolete callbacks after stopping or changing accounts still require review.

Session files now use bounded staging followed by an atomic rename, with checked relative paths and file types. Missing, truncated or oversized attachments fail without deleting the previous file. The receiver preserves the remote modification time, keeps equal or newer local files, and checks the target again before replacement. Copying runs off the main actor; cancellation waits for the file worker before releasing the conversation reservation. The V1 sender now includes file modification time; reception from older V1 senders uses CloudKit's modification date. The receive limit is 64MiB, covering the sizes offered by the upload settings. Eleven portable file tests passed, including cancellation and edits during staging. Darwin rename, symbolic-link behavior and CloudKit asset delivery still require Apple-platform validation.

Force Pull reads every query page and validates the parent session, child ownership, message bodies and summary records before entering one SQLite replacement transaction. A failed fetch, decode or SQL write preserves local messages, attachments and pending sync records. Local conversation bindings remain in place. This is a local atomic replacement, not a transactional snapshot of CloudKit queries. Stopped transports reject the query. ## Product identity and releases

About displays Nivo Bot, the installed package version, the project website, model setup, downloads, issue reporting, the license and upstream credits. `scripts/rebrand.py --ios-brand-only` regenerates visible iOS branding without changing bundle IDs, data directories or versions. This migration does not bump the installed iOS version.

Update checks require an explicitly published stable iOS entry with an IPA, TestFlight or App Store destination. An Android APK or an unqualified release tag does not become an iOS update. A website declaration that iOS is unpublished is shown directly. GitHub fallback also requires an actual IPA asset. The new parser has portable coverage; the live download service and device installation have not been tested as part of this local work.

`NanoMuseOffline.isOn` disables three entry points in this personal build: GitHub-star prompts, relay nudge fetching and relay conversation sync, including when an earlier Cloud sign-in remains stored. It is not a global network block. The provider catalogue remains available for adding providers. This policy does not establish that every configured model was added manually or that the app makes no automatic network requests.

## Clearing, deleting and retrying chat

Clearing a chat, deleting a turn, editing an earlier message and retrying from a message or tool step now commit database changes before updating the screen or starting the model. The composer displays saving progress and is temporarily disabled. Failed writes retain the original history and draft. Missing anchors or a changed database message sequence require a reload rather than deleting by an outdated row count.

Messages, legacy reference copies, deletion markers and outgoing deletion requests commit together. Clearing also removes summaries. Trimming or rewriting invalidates previous summaries; the retained history can be compacted again. Tool-step retries trim the saved content directly, preserve earlier tool signatures and snapshots, and continue the existing assistant bubble. Replacement attachments retain their original input files until the database commit succeeds, with newly staged copies removed on failure.

Single and batch conversation deletion hide rows and clean attachments only after a successful transaction. Relay message deletion validates conversation ownership and handles both historical UUID cases together. Scheduled retries keep a separate edit reservation if their run expires while saving and check the run identity again before starting the model. Thirteen real SQLite tests and two reservation tests passed. UIKit, SwiftUI, attachment and scheduler integration still require Apple-platform acceptance. Relay checkpoint persistence and obsolete callbacks after stopping or changing accounts remain under review.

## Validation

## Relay sync recovery

The relay state file now reports decoding and write failures instead of replacing a damaged account table with an empty one. Cursors, deferred messages and deletion queues are published only after the complete account table is saved. Reads can retry after a locked or unavailable file becomes accessible; a malformed file is retained for recovery.

Uploads, downloads, deferred-message writes and data-control requests share a single operation lease. Requests and delayed callbacks retain the account, credential, relay address and account generation that started them. Disabling sync, changing its scope or signing in again invalidates old results. The lease stays held until the actual operation returns, so backup or account switching cannot begin while it is still writing.

New remote conversations reserve a persistent local ID before database creation. A failed insertion retries with that ID; deletion markers prevent a removed conversation from being recreated. Uploads send conversation batches before message batches and confirm a conversation's timestamp only after all batches finish. Strict message-ID reads detect local clearing even when the conversation timestamp did not change. An unreadable database is not treated as an empty history. Invalid or nonadvancing response pages leave the cursor available for retry.

Twenty-three portable tests cover the real state files, lifecycle rules, response decoding and SQLite operations. Four additional ChatStore application cases are prepared but have not run on an Apple host. URLSession interruption, rapid toggles, account switching, lock-screen file access, large-history performance and restart recovery still require application testing. ## Sync deletion, summary reversion and credential saving {#sync-deletion-and-credentials}

Relay uploads compare actual message IDs, so new messages written within the same second are not skipped when the conversation timestamp is unchanged. New-message uploads also include conversation metadata, allowing sending after a relay wipe while retaining acknowledgement of older messages. Acknowledged history is not decoded again. Tool rows without uploadable text may still be scanned; long-history performance needs iPhone measurement.

Remote main-chat deletion preserves local conversation settings, clears its contents and assigns a new relay ID. A SQLite receipt prevents replay of the same deletion from removing messages written afterwards. Local deletion clears the previous main mapping and message origins. Remote title changes are no longer blocked by a newer local activity timestamp. Reverting one summary commits its deletion, tombstone and pending sync record together; failure retains the summary.

Ordinary provider-key sync validates the complete input before updating Keychain in place. The value and its modification version share one system write. A newer version advances even when the value is identical, preventing a later, older value from overwriting it. Provider creation, import, configuration tools and authorization check the save result. OpenRouter debug logging no longer includes an API-key prefix.

Environment metadata now stores an optional modification time compatible with older files. Per-variable sync rejects malformed Base64, invalid names and field-type errors instead of acknowledging them as empty values. Older or equal versions do not replace saved metadata, and retries retain the actual edit time. Rename saves the new value and metadata before removing the previous name. A target name owned by another record is retained as a conflict instead of overwriting its secret. Read and save failures retain outgoing and incoming retries, and failed forms retain their input. Damaged metadata displays an error and retry action. Legacy whole-file metadata fills missing records or applies explicitly newer versions, including on iOS 16.

## Environment-variable recovery {#environment-variable-recovery}

Environment-variable changes now write a recovery journal before touching credentials. The journal contains metadata, operation identifiers and progress, without secret values or their hashes. Temporary secret values and the previous credentials needed to verify cleanup stay in a separate device-only Keychain item. After an interruption, the app either cancels an operation that never staged credentials or completes the remaining credential, metadata and cleanup steps. A damaged journal or an unexpected metadata file is retained and reported rather than overwritten.

Renaming and deleting a variable retain the old name until cleanup succeeds. Cleanup compares the captured value and version before removing an unchanged credential. Local edits keep a receipt until the SQLite sync queue and deletion protection are committed together. A queue failure can therefore retry after restart without losing the deletion. This does not establish safe behavior for every external iCloud Keychain race, which still needs multi-device testing.

Recovery runs after backup rollback during startup, and retries when the app returns to the foreground, the settings page reloads or sync retries. Backup import and export freeze environment edits, including when only configuration categories are selected. Scripts and the terminal report an incomplete or unreadable environment instead of running with an empty or mixed configuration. The settings page keeps its retry entry on failure. The legacy whole-file sync path uses the same recovery protocol, accepts later arrival of a missing secret and rejects secrets without corresponding metadata. Failed legacy uploads retain their pending record.

## OAuth cancellation and late replies {#oauth-lifecycle}

OAuth logins now carry an operation identity tied to the account and provider restore generation. Signing out, removing a provider, discarding setup or starting a restore invalidates old replies before they can write credentials. A replacement login prevents background callers from refreshing the previously stored credential until that login finishes. Refresh success also compares the credential observed before the network call with the value currently stored; a changed or removed value is preserved. This comparison is not a system transaction against another device's iCloud Keychain writes.

Concurrent callers still share one refresh per provider instance and login generation. Cancelling one caller rejects its result without cancelling a refresh needed by another caller. An old task's cleanup cannot remove a newer refresh. Setup and detail pages retain login task handles, cancel their own tasks on exit and reject results from an earlier form or account. Kimi's success delay respects cancellation. Antigravity sign-out clears the discovered endpoint alongside its project data. Authentication request bodies, token response bodies and callback URLs are no longer printed to debug logs.

These are local source changes. Portable tests exercise the production refresh coordinator and operation state, including cancellation, replacement login and credential changes. Browser presentation, device-code flow, locked-device Keychain behavior and full application type checking require an Apple host. Ordinary provider deletion and JSON import still need persistence and interruption recovery work; these OAuth changes do not establish that those transactions are complete.


## Recoverable single-provider import {#single-provider-import}

Importing a provider JSON now validates the complete model list and credentials before changing storage. A provider restore lease freezes account changes and concurrent configuration work. The existing backup journal records SQLite and JSON rollback snapshots plus the receipt identifying credentials inserted by this import; it does not store credential values. The importer submits one complete candidate configuration and reports success after persistence and journal confirmation.

A credential or configuration failure restores the original configuration and removes only credential entries still bearing this import's receipt. A failed rollback retains recovery materials for startup recovery. If the commit marker is already removed and only old-snapshot cleanup fails, the import stays committed instead of prompting a duplicate import. Configuration pages show progress while waiting. The chat share sheet preserves its file and remains available to retry after a failed import.

## Recoverable provider removal {#provider-removal}

Removing a provider now saves its deletion intent and stages credential comparison data in device-only Keychain before changing configuration. SQLite and JSON saves, deletion protection and the sync queue must be confirmed before the old credentials are cleaned up. Failed cleanup or cache reload keeps a recovery journal and a retry notice in both settings layouts, even when the provider row has already disappeared. Account sign-out uses its existing account lock, and startup recovery completes before normal writes resume.

Deletion includes model database IDs and composite references, affected groups and custom thinking rules. Groups created empty are retained; groups made empty by this removal are deleted, while mixed groups keep their other members. Startup preserves legacy deletion metadata from the JSON mirror. The deletion version includes the affected groups' stored timestamps, and transaction receipts survive ordinary 30-day tombstone pruning. Credential comparison protects later local updates; external iCloud Keychain races still need device tests.

## Provider setup confirmation {#provider-setup-confirmation}

New API-key, browser OAuth and manual-token setup now use the single-provider import recovery boundary. Configuration and pending sync records must be saved before the form reports success. The catalogue and local-server pages use the same entry point; fetched models and an optional default group belong to the candidate configuration. Existing default choices are retained. Duplicate model IDs are collapsed, voice-template capabilities survive a text-only API description, and an actual OAuth model list takes precedence over its built-in fallback list. A local server can fetch models without creating an empty Keychain credential.

Catalogue key checks pass the candidate key directly to the model request. A refused key no longer temporarily replaces the saved key. Updating an existing key compares both its observed value and version after the network response; a later local edit causes a conflict. The form retains input and reports storage failures. Only the form's own restore operation can refresh its provider generation. Restoring settings elsewhere or switching accounts leaves the old form invalid.

Key rotation now keeps its credential rollback material and sync-queue receipt in `BackupRestoreJournal`, alongside the configuration snapshot. Model candidates retain their full semantics across setup and rotation. Recovery removes only this transaction's queue changes and preserves later credentials. Deletion settles the draft registry before releasing its cleaned journal, so restart cannot turn a completed cleanup into a new deletion. Genuine storage failures retain recovery; lost credential ownership instead produces a terminal preservation result.
